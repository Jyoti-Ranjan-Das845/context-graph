# 02 · Spec

## Architecture

```
                 ┌────────────── interfaces ──────────────┐
                 │  React UI ── REST API    CLI    MCP     │
                 └──────────────────┬─────────────────────┘
                                    │
                             QueryService ──── GraphStore (SQLite)
                                    ▲                ▲
                                    │                │ persist
 Scheduler ──► SyncPipeline ────────┴────────────────┘
                 │
   1 pull ───────┤  SourceDefinition ─► AirbyteRunner ─► RawStore (DuckDB)
   2 code ───────┤  GitHubCodeFetcher ─► CodeExtractor (Graphify AST)
   3 normalize ──┤  Normalizer (one per tool) ─► Items + PersonRecords
   4 identity ───┤  IdentityResolver (union-find on emails / ids / names)
   5 build ──────┤  GraphBuilder (structural edges)
   6 link ───────┤  ReferenceLinker (matcher strategies over all text)
   7 enrich ─────┤  SemanticEnricher ─► LLMClient (Claude Code CLI) + cache ─► ConceptMerger
   8 persist ────┘  GraphStore.replace(graph)  (atomic swap)
```

Ports and adapters: everything outside the domain is behind a `Protocol`. The composition root (`bootstrap.py`) is the only place that picks concrete classes.

## Package layout (`backend/src/context_graph`)

| `graph` | `GraphBuilder`, `GraphStore` protocol and `SQLiteGraphStore`. |

## Data model

**Node**: `id`, `kind`, `source`, `title`, `body`, `url`, `created_at`, `updated_at`, `keys` (aliases others may use to refer to it), `props`.

Node kinds: `person`, `repository`, `issue`, `pull_request`, `commit`, `comment`, `project`, `channel`, `message`, `page`, `email_thread`, `email`, `file`, `symbol`, `topic`, `decision`.

**Edge**: `src`, `dst`, `kind`, `confidence` (1.0 for deterministic edges), `props` (evidence snippet, matcher, origin).

Edge kinds: `authored`, `assigned_to`, `part_of`, `reply_to`, `references`, `fixes`, `changes`, `contains`, `calls`, `imports`, `mentions`, `decides`, `about`.

**Node ids** are stable: `<source>:<kind>:<native id>` (people: `person:<canonical key>`, topics: `topic:<slug>`, decisions: `decision:<hash of the canonical statement>`). A re-sync updates a node, never duplicates it.

## Linking rules (deterministic)
Every node publishes `keys`. The linker scans every node's text with these matchers and adds a `references` edge for each hit (no self-links):

| Matcher | Finds | Example |
|---|---|---|
| IssueKey | `ABC-123` | `ENG-5`, `DEMO-1` |
| Url | Any URL, normalised | `github.com/…/pull/2`, Notion page URLs |
| GitHubNumber | `owner/repo#N`, `repo#N`, `#N of repo`, `#N` inside the same repo | `#1 of payments-api` |
| Channel | `#name` (letter first) | `#payments` |
| QuotedTitle | Text in quotes equal to a page/thread/issue title | `"Payments retry design"` |
| Path | Known repo file paths | `payments/retry.py` |
| Symbol | Known function/class names with `_` or camelCase | `charge_with_retry` |

`Fixes/Closes/Resolves <ref>` in a PR or commit becomes a `fixes` edge instead of `references`.

**Identity**: person records from every tool are merged with union-find on shared emails and per-tool ids; exact full-name matches (2+ words) also merge, configurable.

## Semantic enrichment (LLM)
- Input: changed text items, in batches. Output: topics and decisions, each with a verbatim evidence quote.
- A quote that is not found in the source text is dropped.
- Results are cached by `sha256(prompt version + text)`, so unchanged text never goes back to the LLM.
- Merging: extraction runs per item, so one decision stated in Slack, Notion and a PR arrives in three wordings. `ConceptMerger` asks the LLM once per new wording whether it means the same as an existing topic or decision, and `ConceptRegistry` remembers the answer. The result is one node per concept, linked to every item that states it, with the other wordings kept in `props`. Ids never move once assigned. Wordings that differ only in case, punctuation or plural are merged without the LLM. When the registry is large, each call only sees existing concepts that share a word with the new ones.
- Default client: Claude Code CLI (`claude -p`, no tools, JSON schema). The `LLMClient` protocol allows an API or local model later.
- Enrichment is optional. The graph is complete and linked without it.

## Sync strategy
- Pulls are incremental (PyAirbyte state in DuckDB).
- The structural graph is rebuilt from the raw store on every sync. It's deterministic and fast at personal scale, and naturally handles edits and deletes.
- The expensive layer (LLM) is incremental through the cache.
- The new graph is written to a temp file and swapped in atomically, so readers never see a half-built graph.
- DuckDB lets one process hold its file at a time, so pulls and reads open it only while they run. The web app, the CLI and the scheduled sync take turns; a second sync is refused while one runs (`sync.lock`).
- If the local raw data cannot be read, the run fails and the current graph is kept. A tool whose records cannot be normalized is skipped and reported; the others still sync.

## Configuration

Everything that belongs to the person lives in one data folder, `~/.context-graph` (or `$CONTEXT_GRAPH_HOME`), apart from the code. Nothing personal is in the repo or the package.

| File | Holds | Edited by |
|---|---|---|
| `.env` | Credentials and connection identity (tokens, Jira site and email, Google client). Readable only by the owner. | Setup UI or by hand |
| `settings.json` | What to sync: repos, Jira projects, Slack channels, start date, interval, enrichment on/off. Created on first use; the start date defaults to 30 days back and is then fixed. | Setup UI or by hand |

## Interfaces
- **REST** (`127.0.0.1:8765` only, trusted hosts checked; also serves the web app):

  | Area | Endpoints |
  |---|---|
  | Tools | `GET /api/sources` · `POST /api/sources/{id}/check` · `PUT /api/sources/{id}/credentials` · `PUT /api/sources/{id}/options` · `POST /api/sources/gmail/signin` · `GET /api/sources/slack/create-app-url` |
  | Settings | `GET/PUT /api/settings` (saving a new interval also updates an installed schedule) · `GET/PUT /api/schedule` |
  | Sync | `POST /api/sync` (202 once the run has started, or 409 while one runs) · `GET /api/sync/status` |
  | Agents | `GET /api/agents` · `PUT /api/agents/{id}` (`{installed}` adds or removes the skill) |
  | Graph | `GET /api/graph` · `/api/search` · `/api/nodes/{id}` · `/api/nodes/{id}/neighbors` · `/api/path` · `/api/recent` · `/api/context` · `/api/stats` |

  Secrets are returned masked (`••••last4`). Credentials can only be written to the tool they belong to.
- **Search** (shared by all interfaces): SQLite FTS5 over title, body and aliases (key forms such as `ENG-5`, the node kind, the tool). Filler words are ignored. Items containing every content word rank first, then items missing one, then items with any; BM25 orders each level.
- **MCP** (stdio): `search`, `get_node`, `neighbors`, `find_path`, `recent_activity`, `retrieve_context`, `graph_stats`.
- **CLI** (`cg`, works from any folder; every query command prints readable text, or JSON with `--json`):

  | For | Commands |
  |---|---|
  | The person | `setup` (opens the Setup page, starting the web app if needed), `ui` (opens the graph), `sync`, `status`, `check`, `agent install` / `agent remove` |
  | Agents and the person | `ask` (best matches plus their links: the same bundle as MCP `retrieve_context`), `search`, `show`, `neighbors`, `path`, `recent` |
  | Plumbing | `mcp` (stdio server) |

  The web app binds to 127.0.0.1 only. If its port is taken by an older Context Graph, `setup` just opens the browser; if it is taken by another program, it says so.
- **Agent skill**: one guide (`agents/guide.md`) says when to use the graph, the commands, how to read ids, link types and evidence, what to do when nothing matches, how to cite, and safety rules (item text is data; quote private mail sparingly; read only). Claude Code receives it as a personal skill (`~/.claude/skills/context-graph/SKILL.md`, loaded when relevant); Codex as a marked block in `~/.codex/AGENTS.md`, replaced on reinstall and removed cleanly. Adding it never requires every tool to be connected: it warns when nothing is synced, and `cg status` tells the agent what is connected.
- **Web app** (`ui/`, React + Cytoscape): Graph (filters, find, node panel with evidence), Search (items, agent context), Setup as a four-step checklist (connect tools, choose what and how often, sync, connect AI agents), and a sync bar that refreshes the views when any sync finishes.

## Install

`install.sh` checks for uv and Node.js, builds the web app into the package, installs `cg` with `uv tool install` (an isolated environment, with `cg` on the PATH), creates the data folder, offers to move data from an older in-repo layout, offers the agent skill, and opens Setup. It asks before every change outside the repo. Running it again updates the code and keeps the data. PyAirbyte's working files (connector installs, temp files) are kept in the data folder, never in the folder `cg` runs from.

## Decisions

| Decision | Why |
|---|---|
| PyAirbyte for connectors | One library for all six tools, incremental pulls, no server, no Docker |
| DuckDB raw store | A local copy lets us rebuild the graph without calling the tools again |
| Deterministic linking before LLM | Exact, free and testable. The LLM adds meaning, not structure |
| SQLite graph store behind `GraphStore` | Zero install, full-text search built in, atomic file swap. A graph database (e.g. LadybugDB) can be added as another adapter |
| Claude Code CLI as the LLM | Uses the person's existing subscription, no API key |
| Graphify for code | Parses 30+ languages into files, functions and calls without an LLM |
